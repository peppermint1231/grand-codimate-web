# 영구삭제·백업·복구 코드 감사 — 2026-10-18

## 현재 운영에 적용할 지침 — 2026-10-23 보충

이 문서의 아래 감사 본문은 **2026-10-18 / 0.18.35 당시의 역사적 결과**로 보존한다. 당시의 `permanentDelete` 설명, `… → done` 처리 순서와 580개 테스트 결과를 최신 구현이나 현재 운영 삭제 완료의 증거로 사용하지 않는다. 아래의 ‘이번 변경’도 당시 감사 변경을 뜻한다.

PR [#56](https://github.com/peppermint1231/grand-codimate-web/pull/56)(0.18.37)은 개인용 OneDrive의 특정 API 미지원 오류에 한해 전용 폴더 정리 → 휴지통 이동 → `awaiting-recycle-bin` → 관리자 실제 영구삭제 → 앱 확인 기록 → `done` 절차를 추가했다. 휴지통 이동과 관리자 확인 전에는 완료가 아니다. 확인자와 시각을 저장하지만 개인용 휴지통의 실제 삭제를 Graph로 자동 검증한 기록은 아니다. PR #56이 보고한 605개 테스트는 아래의 당시 580개 결과와 별개다.

**현재 실행 순서와 제한은 [운영 문서의 개인용 OneDrive 영구삭제 완료 절차](OPERATIONS.md#개인용-onedrive-영구삭제-완료-절차--pr-56--01837-이후)를 우선 적용한다.** 아래 저장 위치별 잔여 사본·기기 정리 항목은 함께 점검한다. 이 보충은 실제 운영 자료 삭제, 기존 작업 재실행 또는 운영 완료 확인을 수행했다는 뜻이 아니다.

## 기준과 검증 범위

- 기준: `main`의 `d5280ae90c71fe4b19351a13c28ce57dde83ca15`, 0.18.35. PR #51(0.18.33), #52(0.18.34) 병합 내용 포함.
- 운영 API, 운영 OneDrive, 운영 환자 파일에는 접근하거나 삭제하지 않았다. 인메모리 SQLite와 가상 Drive 파일만 사용했다.
- 실제 운영 배포 버전·기기별 설치 버전·실제 파일 목록·Microsoft 보존 정책은 코드만으로 확인할 수 없다. 이 문서는 운영 삭제 완료 증명서가 아니다.
- Android 네이티브 구현은 이 웹 저장소에 없다. `src/lib/native.ts`의 호출 계약과 웹 보관 코드를 확인했다. 별도 Android 저장소의 `shared-revision.txt`는 조회되지 않아 현재 설치 APK와의 소스 일치는 확인하지 못했다.

## 결론

기존 구현은 선택 범위 정규화, 서버 레코드 제거, OneDrive 변경 이력 정제, 파일 영구삭제, 공유 파일 보호, 실패 재시도, 복구 중 상호 배제를 이미 제공한다. 이를 재구현하지 않았다.

이번 변경은 **삭제된 메모의 지연 수정에 의한 재생성**, **삭제 정리 중 백업 내보내기**, **정리 도중 저장 위치/계정 변경**을 막는다. 현재 환자 레코드가 없을 때 과거 폴더를 놓치는 경우도 이력 기반 경로 탐색으로 보완한다. 기기·다운로드·외부 설문·독립 백업을 원격 삭제했다고 표시하지 않도록 안내를 수정한다.

다만 이 기능을 '그 사람의 정보가 모든 저장 위치에서 제거됨'으로 해석할 수는 없다. 특히 통합 전 환자 기본정보와 추적되지 않는 옛 파일은 외부 사본과 구별되는 **앱 내부의 추가 검토 항목**이다.

## 삭제 처리 순서와 기존 안전장치

1. 관리자 권한, 최대 30명, 환자 revision, 확인 문구와 선택 범위를 검사한다. 기기 오프라인 큐에는 영구삭제 명령을 넣지 않는다.
2. 기본정보 전체삭제는 모든 범위를 포함한다. 상담 삭제는 사진·금액·문서를 포함한다. 사진·메모·금액만 삭제해도 내용이 들어간 기존 발급물/서명 자료를 함께 정리한다.
3. 삭제 변경분을 OneDrive에 저장한 뒤 서버에 반영하고 영속 정리 작업을 등록한다. 이 시점의 성공 응답과 전체 정리 완료는 다르다.
4. `operations → media → snapshots → inquiries → done` 순서로 나누어 처리한다. 영구삭제 오류는 작업에 남기고 재시도한다. 일반 휴지통 삭제로 조용히 대체하지 않는다.
5. 오래된 커밋을 바꿀 때 정제된 값과 경로를 `pending`에 먼저 보존한다. 삭제 성공 후 재업로드 실패·프로세스 재시작에 대비한다.
6. PR #52의 기록 ID 기반 정리는 유지했다. 환자 통합 전 상담·메모·금액도 현재 선택된 기록 ID로 찾아 이력에서 정리한다. 다른 환자의 자료와 공유 파일은 보존한다.

Microsoft의 [`driveItem/permanentDelete` 공식 명세](https://learn.microsoft.com/ko-kr/graph/api/driveitem-permanentdelete?view=graph-rest-1.0)는 휴지통을 거치지 않는 영구삭제를 정의한다. 테스트는 호출·실패 처리·재시도를 검증하며 실제 Microsoft 계정의 모든 복구/보존 사본을 실증한 것은 아니다.

## 발견 사항 및 이번 보완

| 항목 | 근거 / 영향 | 처리 |
|---|---|---|
| 삭제된 메모에 늦게 도착한 수정 | `note.save`는 행이 없으면 `baseRev`가 있어도 신규 생성했다. 메모만 영구삭제한 뒤 오프라인 기존 메모 수정 요청을 적용하면 재생성됨 | **수정**: 기존 revision을 가진 수정인데 행이 없으면 409. 새 메모 작성은 유지. 수정 전 실패/수정 후 통과 회귀 테스트 |
| 정리 중 새 암호화 백업 | `/backup`은 아직 정제되지 않은 `operations`·media까지 내보낼 수 있었음 | **수정**: 미완료/실패 정리 작업이 있으면 409. 완료 뒤 다시 허용 |
| 정리 중 폴더/계정 변경 | 정리 작업은 시작 시 `root`를 고정하지만 `/storage`, OAuth 연결/콜백은 이를 보호하지 않았음 | **수정**: 폴더 변경을 완료 전 차단. 새 작업은 Drive ID를 고정하고 OAuth 콜백에서 같은 Drive ID와 기존 폴더를 확인한 뒤에만 인증 갱신. 다른 계정은 기존 토큰을 변경하지 않고 거부. Drive ID가 없는 이전 작업은 연결 변경 거부. 외부 OneDrive 수동 이동까지 통제하는 기능은 아님 |
| 현재 환자 행 없이 남은 과거 경로 | 이력의 상담 경로 발견이 살아 있는 환자 entity에 의존. 현재 계획과 다른 과거 폴더가 있고 환자 entity가 이미 없으면 누락 가능 | **방어적 보완**: 이력의 최소 폴더 정보를 암호화한 임시 테이블로 추적. 재시작 이후에도 사용하고 완료 시 제거. 과거/현재 경로가 다른 가상 이력으로 실패→통과 확인. 현재 UI가 상담 구분 변경을 지원한다는 뜻은 아님 |
| 완료 표시의 범위 혼동 | '서버 원본·백업 정리 완료'만으로 독립 백업·기기 사본까지 없다고 오해할 수 있음 | **안내 수정**: 앱이 추적하는 현재 자료 기준임을 명시. 삭제 창·완료 상태·백업·복구 화면과 사용법에 잔여 사본/재등장 안내 |

이번 변경은 APK 제작·운영 배포·기존 완료 작업의 자동 재실행을 포함하지 않는다. 이미 완료된 작업이나 이전 정제 과정에서 사라진 경로 증거를 소급 복구하지 않는다.

| 삭제 전에 만들어졌지만 서버가 한 번도 받지 않은 신규 명령 | 부분삭제 후 부모 환자/상담이 살아 있으면 새 메모·의견·금액 등으로 승인될 수 있음. 전체 명령에 대한 삭제 시점/기기 세대 차단 장치는 없음 |
| 삭제 전 폴더 사본을 원본 위치에 덮어쓴 뒤 복구 | 과거 상태 재등장 가능. 삭제 변경분 자체가 사본에 없거나 이후 stale 커밋을 추가하면 복구 순서에 따라 복원됨. 독립 삭제 원장으로 모든 옛 백업을 강제 필터링하지 않음 |
| 내려받은 `.enc` 백업 | 파일 자체는 자동 정제되지 않음. 현재 UI/서버의 복구는 OneDrive 원본 재구축이며 이 `.enc` 파일을 직접 올리는 복구 UI는 확인되지 않음 |
| 외부 설문/가져오기 또는 새 ID로 재등록 | 외부 원본이 남으면 가능. 사람의 동일성을 영구 차단하는 기능은 없음 |
| 오프라인 화면·로컬 미디어/초안 표시 | 서버 재생성과 별개로 기기에서 재노출 가능. 오프라인 로그인 제한 시간이 지나도 암호문이 자동 소거되지는 않음 |

## 추가 설계/운영 점검 항목 — 완료로 간주하지 않음

1. **통합 전 환자 기본정보**: `patient.merge`는 원래 행에 `mergedInto`를 남긴다. purge는 선택 ID의 기본정보를 제거하며 통합 전 행까지 선택 ID를 확장하지 않는다. PR #52의 '연결 기록 이력 정리'와 다르다. 통합 계보를 포함한 삭제 범위를 설계해야 하며, 이 감사에서 연관 환자를 임의로 광범위 삭제하지 않았다.
2. **레거시 원본·추적 상실 파일**: `worker.ts`의 레거시 사진 복사 경로는 기존 원본을 보존하고 메타데이터 remoteId를 새 파일로 교체한다. 기존 원본 ID, 수동 사본, 이름 변경된 파일까지 완전하게 열거하는 보관 목록이 없다. 이전 파일·폴더 이름도 점검해야 한다.
3. **미전송 신규 작업과 기기 자료**: 지금은 수정 충돌/이미 지운 media ID 차단 중심이다. 기기별 확인, 환자별 로컬 삭제, 삭제 기준 시점 전 신규 명령 차단, 복구 시 삭제 원장 적용은 별도 기능이다. 기존 앱에 그런 기능이 있는 것처럼 안내하지 않는다.
4. **로그·접수·외부 통계**: 조회 흔적 및 연결되지 않은 접수/외부 설문 파생 정보까지 '개인 전체 소거'에 넣을지는 범위를 명시해야 한다. 기존 로그를 무단 삭제하지 않는다.
5. **실서비스 상태**: 실제 파일 잔존 여부와 Graph 계정별 영구삭제 권한, 기기 캐시, 외부 스냅샷은 운영 자료를 지우지 않고 별도 점검해야 한다. 코드·가상 테스트만으로 그 위치가 비었다고 판단하지 않는다.

## 관리자 잔여 사본 정리 절차

1. 대상 환자 ID·선택 범위·관련 상담 ID·통합 이력·삭제 작업 ID를 기록한다. 전 직원 사용 기기/계정, 외부 설문 앱, 독립 백업 위치를 목록화한다. 실제 환자로 연습하지 않는다.
2. 삭제 대상의 오프라인 신규 작업·초안·충돌 자료가 있는 기기는 무조건 '전송 재시도'하지 않는다. 대상 자료를 다시 전송하지 않게 업무를 중지하고, 다른 환자의 미전송 자료를 구분해 보존/확정한다.
3. 승인된 서버 삭제를 실행하는 운영 절차에서는 정리 완료까지 확인한다. 오류면 기존 작업을 재시도한다. 인증 만료라면 새 방식으로 시작한 작업은 같은 OneDrive 계정과 기존 폴더를 확인한 뒤 재인증할 수 있다. Drive ID가 기록되지 않은 이전 작업은 안전한 계정 확인이 안 되므로 연결 변경을 거부한다. 완료 전 백업/복구/폴더 변경/다른 계정 연결 및 OneDrive에서의 직접 폴더 이동을 하지 않는다.
4. 모든 기기의 암호화 보관, 초안, 전송 대기, 복구 자료, 사진 캐시를 확인한다. 현재 앱에는 환자별 기기 삭제 버튼이 없다. 전체 제거가 필요하면 **다른 환자의 미전송 자료를 먼저 보존·확정한 뒤** 브라우저의 해당 사이트 데이터(IndexedDB 포함) 또는 Android의 앱 저장 데이터 삭제를 기기별로 수행한다. 이는 모든 계정의 로컬 자료·로그인/설정을 지울 수 있으므로 단순 로그아웃과 구분한다. 여러 브라우저 프로필/앱도 각각 확인한다.
5. 다운로드 폴더·선택 저장 폴더·PC 동기화 사본·공유 파일·인쇄물·휴지통, 내려받은 `.enc`와 이전 루트 복사본을 별도로 확인한다. 다른 환자가 섞인 백업은 통째 삭제하지 말고 보관 범위에 맞게 관리한다. 삭제 전 백업을 활성 원본에 되돌리지 않는다.
6. 외부 초진설문 앱의 원본과 태블릿·동기화 파일·PNG·백업을 그 앱의 절차로 정리한다. 대상 환자와 연결된 설문인지 확인하고 다른 설문을 보존한다. 코디메이트의 외부 설문 동기화를 완료한 후 검색/통계 반영도 확인한다.
7. 통합 전 기본정보·과거 사진 원본·수동 사본·조회 기록은 위 '추가 설계/운영 점검' 항목으로 남긴다. 위치별로 `확인 완료 / 잔존 / 미확인`을 기록한다. 서버 정리 완료만으로 모든 사본 정리 완료 처리하지 않는다.
8. 삭제 완료 후의 원본으로 새 백업을 만든다. 복구 시험은 격리된 환경과 가상 자료로 먼저 수행하고, 삭제 대상 부재·다른 환자 보존·미디어 접근 차단·지연 명령 거부를 확인한다.
